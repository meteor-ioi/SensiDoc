# SensiDoc 阶段性架构与工程评估报告 (Phase 92, 94, 95)

> **评估范围**：
> - **阶段九十二**：纸质文档与密集表格 OCR 识别原生集成 (PP-OCRv6 + SLANet_plus + 卷帘透视比对)
> - **阶段九十四**：`anyocr` 引擎底座同步升级 (CoreML 优化、多核 SIMD、2560px 视窗自适应保护与坐标逆变换还原)
> - **阶段九十五**：文本识别 (Rec) 模型全面轻量化 (切换至 `PP-OCRv6_rec_small`，总体积缩减至 ~39MB)
>
> **评估时间**：2026-09-13  
> **评估视角**：资深软件工程师 (Senior Software Engineer / Systems & Architecture)

## 1. 核心工程亮点 (The Good)

### 1.1 架构分层得当，解耦节奏教科书级
在技术选型与模块演进上，团队遵循了标准的“先打通端到端、后提炼公共底座”的敏捷演进策略：
- **阶段 92** 先在 `src/ocr/` 内部完整实现 6 个核心子模块（预处理、DBNet 检测、SVTR 识别、SLANet 表格、几何拓扑匹配、Markdown 组装），以最短链路跑通原型与业务闭环；
- **阶段 93** 在验证可行性后，果断将底层算法与推理重型模块外提至独立的 `anyocr` 感知库，SensiDoc 侧仅保留 266 行极轻量的门面适配层 (`src/ocr/mod.rs`)；
- **阶段 94** 顺畅升级上游底座，上游能力的演进（如 2560px 视窗自适应钳制、CoreML 优化）只需微调配置，业务代码几乎零震荡。

避免了“过早抽象”的空转，也杜绝了“抽象不足”导致的架构腐化。

### 1.2 务实高效的嵌入式推理生命周期管理
在端侧桌面应用场景下，深度学习模型常驻内存与冷启动时延是一对经典矛盾。SensiDoc 的工程折中设计非常务实：
- **惰性单例按需载入**：非图片/扫描件场景下零内存开销；
- **空闲超时自动卸载**：后台 Tokio 协程每 30 秒轮询，3 分钟无新请求自动卸载 ONNX Runtime 会话并释放内存；
- **引用计数并发安全**：通过 `Arc::strong_count == 1` 确保无外部正在执行的推理任务时才执行释放，防止任务中途崩溃；
- **状态监控单次启动**：采用 `compare_exchange` 保证全局监控任务唯一性，避免重复 spawn。

### 1.3 极具性价比的轻量化选型 (阶段 95)
文本识别模型从 `PP-OCRv6_rec_medium` 切换为 `PP-OCRv6_rec_small`：
- 单模型体积由 **76.6MB 骤降至 21.2MB** (📉 -72.3%)；
- OCR 全套总包由 **94.4MB 骤降至 38.9MB** (📉 -58.7%)；
- 单图端到端推理时延从 **~2490ms 缩减至 ~1314ms** (⚡ 提速约 47%)；
- 内存峰值减半。
对于 SensiDoc 专注于中文增值税发票、财务收据、报关单与物流单据的场景，Small 模型已能达到 98%+ 的可用准确率，以极小的精度微损换取了巨大的下载、内存与吞吐优势。同时在 `paths.rs` 中设计了 `small -> medium` 的向后兼容回退，老用户资产平滑过渡。

### 1.4 真实样本驱动的高健壮性防御设计
在 PDF 扫描件路由和拓扑排序中，体现了深厚的工业踩坑沉淀：
- **PDF 页面旋转递归继承**：针对内嵌扫描图横向但 PDF 标明 `/Rotate 270` 的倒向样本，遵从 ISO 32000-1 规范递归溯源 `/Parent` 树继承属性，自动执行内存图像正向矫正；
- **排序异常熔断防 Crash**：针对密集阶梯状文本框破坏 IEEE 浮点数学全序导致标准库 driftsort panic 的极端场景，引入严格 `total_cmp` 分桶与 `catch_unwind` 异常兜底，优雅回退而非导致进程崩溃。

### 1.5 前后端交互全链路闭环
UI 层面打造了“模型未安装情境拦截 -> 一键原位下载与进度反馈 -> 自动恢复文档处理 -> 视界拨杆与 CSS clip-path 硬件加速卷帘比对”的高品质闭环，彻底消除了传统 AI 工具“让用户自行去外部下载模型配置路径”的断层体验。

## 2. 潜在风险与技术债剖析 (Risks & Technical Debt)

### 2.1 依赖库泄漏开发私有路径 (需清理)
在 `anyocr/src/asset/downloader.rs:60` 中硬编码了开发者本地绝对路径：
```rust
let sensidoc_dir = PathBuf::from("/Users/icychick/Projects/SensiDoc-ocr/models/ocr");
```
- **风险分析**：`anyocr` 已经发布到开源 GitHub 仓库，作为独立库引用时，所有外部用户机器上都会多余探测该不存在的路径；虽然跳过不报错，但属于不该泄露进公共库的内部实现细节。
- **改进建议**：移除该绝对路径，或将其置于 `#[cfg(debug_assertions)]` 内部，通过环境变量 `ANYOCR_CACHE_DIR` 统一接管。

### 2.2 SensiDoc 顶层依赖冗余 (Cargo 卫生)
在 SensiDoc 的 `Cargo.toml:46-49` 中：
```toml
ort = { version = "2.0.0-rc.9", features = ["download-binaries", "copy-dylibs"] }
ndarray = "0.17"
imageproc = "0.25"
```
- **风险分析**：阶段 93 解耦后，重型底层依赖已下沉给 `anyocr`。目前 SensiDoc 主代码库中完全没有直接调用 `ndarray` 和 `imageproc`，`ort` 也是通过 `anyocr` 内部使用。保留在顶层会导致依赖重复声明、版本升级不同步以及潜在编译链接冲突。
- **改进建议**：从 SensiDoc 的 `Cargo.toml` 中移除 `ort`、`ndarray`、`imageproc`，仅保留直接调用的 `image` crate。

### 2.3 下载与状态探测缺乏强类型校验 (Hash / Checksum)
- **风险分析**：`download_ocr_bundle` 目前仅依据 Content-Length 和字节大小范围判定文件就绪；若用户在恶劣弱网环境下发生数据流截断或 CDN 传输损坏，残缺的 ONNX 模型文件可能刚好满足大小阈值，导致模型加载时静默失效或输出乱码。
- **改进建议**：在 `OcrDownloadFileSpec` 中引入官方 `sha256` 校验指纹，文件下载完成或首次校验时计算 hash，确保模型文件绝对完整。

### 2.4 全局静态锁在 Panic 穿透下的潜在状态不一致
- **风险分析**：`OCR_STATE` 使用了全局 `std::sync::Mutex`。当前代码处理了 `match OCR_STATE.lock() { Ok(l) => l, Err(_) => continue / return false }`，虽然不会 panic 崩溃，但静默忽略 PoisonError 意味着发生过跨线程 panic 后的状态未得到显式告警或恢复。
- **改进建议**：在锁中毒（Poisoned）分支中显式增加 `tracing::error!` 日志输出，并在必要时重新初始化内部 `OcrStateHolder`。

### 2.5 前后端文案硬编码散落耦合
- **风险分析**：`~39MB` 这个体积数字当前硬编码分散在 `src/ocr/mod.rs`、`src/converter.rs` (两处)、`web/index.html` (三处)、`web/app.js` (两处) 共 8 个位置。未来若模型规格微调，全文搜替极易遗漏。
- **改进建议**：后端统一由 `get_ocr_total_expected_bytes()` 动态返回 `total_bytes`，前端从 `/api/ocr/status` 动态格式化渲染，消除手工同步技术债。
