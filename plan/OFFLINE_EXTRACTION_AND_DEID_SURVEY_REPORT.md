## 一、 执行摘要与痛点定性

在企业离线内网、纯 CPU 运行环境中，使用 $\le$ 1.5B 生成式小模型或单一正则进行文档信息提取与脱敏时，普遍面临两大核心痛点：
1. **误报（False Positives / 越界提取）**：正则将合同订单号、普通流水号误当手机号/身份证；小模型在上下文提示下提取了“未要求的相似字段”（如把发票代码当发票号码）。
2. **漏报（False Negatives / 遗漏敏感项）**：由于长文本注意力衰减或句式变化，隐蔽人名或长实体未被检出，在脱敏合规场景下构成安全事故。

**核心结论**：在纯 CPU 离线架构中，**严禁将抽取与脱敏全链路单赌在 1.5B 自回归小模型上（端到端）**。必须将**识别（Analyzer）**与**处置（Anonymizer）**彻底解耦，采用“**数学校验和 + 上下文线索加权 + 专用判别小模型 + 结构化约束解码**”的神经-符号分级流水线。

## 二、 底层机理剖析：1.5B及以下模型指令遵循与提取失效根源

```text
┌────────────────────────────────────────────────────────┐
│ 输入端 (Prompt 序列)                                   │
│  [System Prompt: 仅提取 A, B, C]  ─── (序列前端)       │
│  [User Context: 包含 A, B, C'（类似C）, D, E...]       │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 1.5B 模型内部推理瓶颈                                  │
│  ├─ 远程注意力稀释 (Recency Bias) ──> 遗忘 C ──────────┼──> [漏提取]
│  ├─ 隐空间表征拥挤 (Low Dim)     ──> C' 与 C 语义重叠 ─┼──> [混淆提取]
│  └─ 缺乏抑制回路 (No Inhibition)  ──> 遇到 D 强自回归 ─┼──> [多余提取]
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 输出端 (Logit 竞争失衡)                                │
│  生成结果: { A: ..., B': ..., D: ... } (逻辑全面失守)  │
└──────────────────────────┘
```

1. **语义流形拥挤与特征解耦失败（提取“相似字段”的主因）**  
   1.5B 模型隐藏层维度（Hidden Size）通常仅为 1536 左右。高维空间能将“发票代码”与“发票号码”在几何超平面上严格分开；但低维空间中细粒度语义的边界极模糊，相似词余弦相似度虚高，产生语义混淆泄漏。
2. **缺乏门控抑制回路（Inhibition Circuits，刹不住车）**  
   大模型拥有足够深宽的前馈网络（FFN）抑制无关 token 的激活。小模型缺乏多级否定与筛选逻辑，上下文一旦出现 Key-Value 格式，受预训练习惯诱导会本能地按格式补全输出。
3. **注意力通道稀缺与就近偏置（Recency Bias，漏提取主因）**  
   System Prompt 处于序列最前端。因果注意力天然向就近上下文倾斜，随着文档长度增长，有限的注意力头被正文局部词占据，系统约束信号在深层网络中被稀释冲淡。
4. **蒸馏对齐的表象模仿**  
   开源 1.5B 模型多蒸馏自 70B/405B，学到了大模型说话的语气格式，但未内化“元指令（Meta-instruction）优先级高于上下文数据”的仲裁路由机制。

## 四、 业界标杆开源项目深度借鉴

### 4.1 caipeijia833/doc-redaction：单机离线文档脱敏的极致工程安全

该项目是一个针对法律卷宗、办公文档与多媒体的完全单机离线脱敏系统，其核心亮点在于**生产级威胁模型与安全边界设计**：

1. **失败关闭原则（Fail-Closed）**：
   - 核心哲学：**“宁可停止任务告警，绝不向用户输出看似已脱敏但实际有明文残留的半成品。”**
   - 遇到损坏 XML、加密 PDF、内嵌未解密 OLE/ActiveX/VBA 宏、缺少中文 OCR 依赖时，默认终止任务并明确记录原因，彻底杜绝“假阴性”外发。
2. **PDF/版式文档“坐标遮挡 + 渲染后置复扫”**：
   - 痛点：仅在 PDF 上画黑框或替换部分字流，底层的不可见文本流或光栅扫描件仍存在明文外泄漏洞。
   - 策略：文本脱敏后高保真渲染为位图，由轻量本地 OCR 再次执行全量“残留复扫”，确认零命中后方可交付。
3. **稳定化名（Consistent Pseudonym）与可逆保险库**：
   - 同一项目批次内，“张三”固定映射为 `[自然人A]`，“李四”固定映射为 `[自然人B]`，保留合同权责指代链条。
   - 结合 PBKDF2（600,000次）+ AES-256-GCM 本地加密原件，支持审计人员凭口令一键 Deanonymize 逆向还原。
4. **单机通信与资源防御门禁**：
   - 仅绑定 `127.0.0.1`，强校验 Host 白名单，启动分配随机会话 Token，防御恶意网页 CSRF 与 DNS 重绑定偷调；
   - 严格解压门禁：限制解压倍率（$\le 200$）、单项展开上限（1GB）、展开总量（8GB），全面拦截 Zip Bomb 与相对路径穿透（`../`）。

### 4.2 Microsoft Presidio：工业级PII识别精准度提升体系

Presidio（10.7k+ ★）之所以能将敏感信息误报率压降到极致，核心在于**四级置信度评分漏斗与上下文动态加权**：

```text
┌──────────────────────────────────────────────────────────────┐
│ 步骤 1: 模式初步匹配 (Base Score)                            │
│  ├─ 结构化实体: 正则表达式初筛 ──────────> 赋予基础分 (如 0.4) │
│  └─ 非结构化实体: NLP / NER 模型识别 ─────> 赋予模型置信度 (如 0.85)
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ 步骤 2: 严格数学校验和 (Checksum Validation)                 │
│  ├─ 银行卡 (Luhn 模10)、身份证 (ISO 7064)、税号等            │
│  └─ 逻辑: 校验通过 ──> 提至满分 (1.0)；校验失败 ──> 直接归零剔除
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ 步骤 3: 上下文感知加权 (Context-Aware Boosting) ★核心杀手锏  │
│  ├─ 滑动探测窗口: 检查前后 5~10 个词                         │
│  ├─ 线索词匹配: 是否出现 ["电话", "手机", "联系方式"] 等     │
│  └─ 动态重打分: Score = Score + Context_Weight (如 +0.35)    │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ 步骤 4: 阈值截断与重叠冲突仲裁 (Conflict Resolution)          │
│  ├─ 过滤掉低于 score_threshold (如 0.6) 的低置信度项        │
│  └─ 重叠区间仲裁: 相同位置重叠，优先选【最高分】与【最长跨度】│
└──────────────────────────────┴───────────────────────────────┘
```

1. **上下文感知加权（Context-Aware Boosting）**：
   - 规则实体配置专属 `context` 线索词。
   - 纯数字命中正则只给基础分（`0.4`）；在前后滑动窗口内若搜到“电话/手机/联系”，加权跃升至 `0.85`，未命中线索词的孤立数字被阈值直接淘汰。
2. **数学校验和（Checksum）硬截断**：
   - 银行卡跑 **Luhn（模 10）算法**；二代身份证跑 **ISO 7064:1983.MOD 11-2** 校验；企业信用代码跑校验位算法。纯数学逻辑在纳秒级内剔除 90% 以上随机数字串误报。
3. **识别与处置彻底解耦**：
   - 识别层只输出标准跨度 `{ entity, start, end, score, trace }`；
   - 处置层支持 `Mask`（星号掩码）、`Replace`（稳定化名）、`Redact`（物理抹除）、`Hash`（带盐哈希）、`Encrypt`（AES 可逆加密）多种算子。
4. **决策链路透明可解释（Explanation Trace）**：
   - 详细记录判定源头、初始分、上下文加分词与最终得分，为审计合规提供完整追溯证据。

## 五、 SensiDoc 核心精准度提升与架构演进路线图

结合 SensiDoc 当前的代码库架构（Rust + Axum + 本地/云端混合提取），建议分阶段推进以下工程落地：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    SensiDoc 演进路线图 (Roadmap)                        │
├───────────────────┬─────────────────────┬───────────────────────────────┤
│ Phase 1: 精度止血 │ Phase 2: 体系解耦   │ Phase 3: 专模专治与工程闭环   │
│ (2~3 天)          │ (1~2 周)            │ (2~4 周)                      │
├───────────────────┼─────────────────────┼───────────────────────────────┤
│ · 身份证 MOD 11-2 │ · 抽象 Recognizer   │ · 集成 ONNX UIE/GLiNER/RoBERTa│
│ · 银行卡 Luhn     │ · 落地上下文加权    │ · 落地稳定化名与 AES 保险库   │
│ · 基础正则边界收紧│ · 区间重叠仲裁      │ · Fail-Closed 与 Zip 炸弹防护 │
│ · 消除 90% 虚警   │ · 拆分脱敏算子库    │ · 本地 Web 随机会话鉴权       │
└───────────────────┴─────────────────────┴───────────────────────────────┘
```

### 阶段一：纯数学算法与规则边界加固（零算力、立竿见影）
* **改造文件**：`src/extractor.rs`
* **落地动作**：
  1. 为 `REGEX_ID_CARD` 增加 ISO 7064 MOD 11-2 末位校验码验证函数；
  2. 为 `REGEX_BANK_CARD` 增加 Luhn 模 10 校验函数；
  3. 过滤掉年份异常（如出生年份大于当前年份或小于 1900）的无效串。
* **预期效果**：零 CPU 算力消耗下，**彻底消除身份证和银行卡在长报表中的绝大部分随机数字误报**。

### 阶段二：识别/处置体系解耦与上下文感知打分
* **改造文件**：`src/extractor.rs`、`src/desensitizer.rs`
* **落地动作**：
  1. 数据结构重构：敏感项增加 `score: f32` 与 `context_traces: Vec<String>`；
  2. 实现滑动窗口词探测，对电话、姓名等弱规则进行上下文匹配加分（如前后 30 字符内出现“电话/联系”加权 0.45 分）；
  3. 实现区间冲突仲裁算法：同位置重叠时，按“最高置信度优先、同分最长跨度优先”裁决；
  4. 处置层解耦：在 `Desensitizer` 中支持 `Mask`、`Replace`、`Encrypt` 等多策略配置。

### 阶段三：集成轻量 ONNX 判别模型（专人专事）
* **改造文件**：`src/extractor.rs`、`Cargo.toml`
* **落地动作**：
  1. 引入 `ort`（ONNX Runtime Rust 绑定）；
  2. 优先集成经过蒸馏的 **UIE-Mini** 或 **RoBERTa-wwm-ext-base-NER**（INT8 量化模型文件约 100MB，内存占用 <150MB）；
  3. 非结构化人名、地名、机构名交由判别模型处理，彻底取代脆弱的模糊正则；
  4. 复杂长难句及审计裁决继续保留给 `Qwen2.5-1.5B (GGUF)` 兜底。

### 阶段四：工程安全与可逆脱敏闭环
* **改造文件**：`src/main.rs`、`src/desensitizer.rs`
* **落地动作**：
  1. 本地 Axum 服务增加启动随机会话 Token 中间件与 Host 白名单校验，防御本地端口偷调；
  2. DOCX/XLSX/PPTX 解压流程增加解压倍率与单项尺寸上限拦截，防御 Zip Bomb；
  3. 增加“稳定化名一致性映射表”与 AES-256-GCM 本地加密保险库，满足高等级法务与财务可逆审计诉求。
