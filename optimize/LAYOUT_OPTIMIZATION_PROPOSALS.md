# SensiDoc 敏感提取规则与 Prompt 调优模块 —— 布局深度重构方案

> **文档定位**：针对 SensiDoc 中间主舞台顶部“敏感提取规则定义与 Prompt 调优”区域的布局不合理、交互繁琐、屏效低等问题，从**资深产品经理**与**高阶产品设计师**视角出发，系统化梳理痛点并输出 3 套差异化且具备高度落地性的重构设计方案。

---

## 一、 现状痛点深度剖析（Product & UX Review）

对照现有设计与用户操作路径，该区域存在以下四个维度的结构性问题：

```text
                     当前设计存在的核心体验断层
 ┌─────────────────────────────────────────────────────────────┐
 │ 1. 空间争夺 (Cannibalization) │ 规则表格占高超 50%，严重挤压核心预览区 │
 ├──────────────────────────────┼─────────────────────────────┤
 │ 2. 交互摩擦 (High Friction)   │ 下拉框逐个选标签、全行输入框视觉疲劳   │
 ├──────────────────────────────┼─────────────────────────────┤
 │ 3. 动线断裂 (Broken Journey) │ 选模板(左)->选标签(右)->改表(中)->提取(右上)│
 ├──────────────────────────────┼─────────────────────────────┤
 │ 4. 心智混杂 (Mental Clutter) │ 业务字段抽取与底层小模型 Prompt 调优杂糅 │
 └──────────────────────────────┴─────────────────────────────┘
```

### 1. 垂直视界挤压严重（Screen Estate Cannibalization）
* **现状**：中间主舞台本应是用户的核心阅读区（核对 Markdown 正文与敏感词标注高亮）。然而当展开 6 条以上规则时，规则区垂直高度超过 360px，吞噬了超过 50%~60% 的屏幕黄金高度。
* **后果**：用户在核对长文档时必须不断上下滚动，或反复手动点击折叠/展开，严重打断核验心流。

### 2. 表单形态过重，微交互摩擦大（High Interaction Friction）
* **“常用字段标签库”采用原生下拉选择框**：用户想添加 3 个字段（如：甲方、乙方、金额），必须进行 3 次重复操作：“展开下拉框 -> 滚动查找 -> 点击选中 -> 页面回弹 -> 重新展开”，效率极其低下。
* **大面积边框输入框引发“表单疲劳（Input Fatigue）”**：每一行都是硬边框的 Input，视觉噪点密布，缺乏层次与留白。
* **单字谜底按钮**：“标”与“删”采用单字按钮。“标”意图模糊（保存为常用标签？还是标记状态？），缺乏认知引导且极易误触删除。

### 3. 操作动线割裂跳跃（Broken Visual Ergonomics）
* 用户视线与鼠标位移轨迹呈“之字形/混乱弹跳”：
  1. 左上角选择【场景预设模板】；
  2. 视线移到右侧选择【常用字段标签库】；
  3. 视线跳到中间表格检查/修改字段内容；
  4. 视线移到最底部点击【+ 新增空白字段】；
  5. 视线突然又跳回最顶端右上角点击【立即提取】。
* **操作流缺乏向心力**，高频动作与配置过程脱节。

### 4. 业务规则定义与 LLM 底层工程混杂
* 表头标有“提取描述 (组合进入 System Prompt)”，直接将底层实现细节暴露给业务用户。
* 既有业务日常使用的“选字段提取”，又有算法调优使用的“Prompt 调优 / 输出契约规范”，两者层级并列，模糊了“日常操作流”与“高级调试流”的边界。

## 二、 重构目标与设计原则

1. **Content-First（内容优先）**：将主舞台的视觉与操作重心彻底交还给文档核对。
2. **Progressive Disclosure（渐进式呈现）**：80% 的高频操作（切换模板、一键提取、点选常用字段）0秒直达；20% 的深度调优（修改Prompt、高级配置）按需呼出。
3. **Zero-Friction Input（零阻力录入）**：告别繁重表格，引入点击即加的标签胶囊（Tag Pill）、行内轻微调与一键批量控制。
4. **Fluid Ergonomics（平滑自然动线）**：统一操作流向，遵循从“选择/配制”到“触发运行”的线性逻辑。

## 三、 三套差异化重构设计方案

```text
 方案 A: 极简沉浸条 + 侧滑配置中心 (Focus & Drawer)  [极简轻量 · 文档沉浸]
 方案 B: 紧凑胶囊网格 + 快捷标签池 (Compact Capsule)  [就地配置 · 零跳转]
 方案 C: 右栏一体化检查台模式 (Unified Inspector)    [专业工作台 · 权责分明]
```

---

### 方案 A：【极简沉浸条 + 侧滑抽屉配置中心】（Focus & Drawer 模式）—— ★ 强烈推荐

#### 1. 核心设计理念
* **“把主舞台 100% 留给正文阅读”**。
* 中间主舞台顶部不再常驻任何大表格，仅保留一条仅 **42px 高的极精致玻璃质感控制条（Summary Bar）**。
* 控制条内展示当前模板、已启用规则芯片（Chips）、一键提取主按钮，以及【配置规则 ⚙️】入口。
* 点击配置或添加时，从右侧（或以浮动抽屉形式）展开独立的【规则与 Prompt 控制中心】，提供充裕舒适的多行配置空间，关闭后主屏幕重归极简纯粹。

### 方案 B：【紧凑胶囊网格 + 快捷标签池】（Compact Tag Pills & Chip Pool 模式）

#### 1. 核心设计理念
* **“就地直接微调，但用现代流式卡片替代笨重表单”**。
* 适合偏好在主界面直观看到并随时增删规则的用户，但将传统 `<table>` 重构为 **高度压缩的胶囊芯片（Tag Pill）流式网格**。
* 将总高度严格限制在 **110px 以内**（比当前减少 65% 的高度占用），支持一键批量开关与气泡微调。

### 方案 C：【右侧栏输入输出一体化工作台】（Unified Inspector Panel 模式）

#### 1. 核心设计理念
* **“重构三栏职责：中间纯舞台，右侧全主控”**。
* SensiDoc 目前的右侧栏是“提取出的敏感词清单”，顶部是“规则配置”。这两者本质上是 **配置（Input）** 与 **结果（Output）** 的因果闭环！
* 将右侧栏升级为【智能审计主控台】，通过 Segmented Tabs 提供两种视图：
  - `[ 敏感词清单 (18) ]`（核对与导出阶段）
  - `[ 提取规则定义 (6) ]`（配置与调优阶段）
* 中间预览区彻底剔除所有配置控件，仅保留极简的面包屑与阅读进度条，获得堪比专业阅读器（如 Notion / Acrobat）的纯粹阅读体验。

## 四、 三大方案综合对比与评估矩阵

| 评估维度 | 方案 A：极简沉浸条 + 侧滑抽屉 | 方案 B：紧凑胶囊网格 + 标签池 | 方案 C：右栏一体化检查台 |
| :--- | :--- | :--- | :--- |
| **主屏阅读空间释放度** | ★★★★★ (释放 95% 高度) | ★★★★☆ (高度控制在 110px 内) | ★★★★★ (释放 100% 空间) |
| **规则编辑舒适度** | ★★★★★ (抽屉空间大、排版舒展) | ★★★☆☆ (需通过 Popover 修改) | ★★★★☆ (右侧纵向长列表) |
| **高频标签添加效率** | ★★★★☆ (在抽屉内一键加) | ★★★★★ (在主页顶栏一键点加) | ★★★★☆ (在右侧栏一键加) |
| **操作闭环动线体验** | ★★★★☆ (配置完关闭/回主页) | ★★★★☆ (就地直接配置并提取) | ★★★★★ (输入与输出无缝切换) |
| **技术改造与现有代码兼容性** | **最高** (原逻辑几乎完全复用) | **中等** (需重构卡片与气泡弹窗) | **较大** (需调整三栏 DOM 职责) |
| **目标用户契合度** | 最适合绝大部分日常业务人员 | 适合高频需要反复调整微词的用户 | 适合专业合规审计与高级分析师 |

## 五、 落地推进建议与实施路径（Implementation Roadmap）

基于敏捷迭代与“小步快跑、收益最大化”的产品原则，建议采取以下两阶段推进：

### 第一阶段（快速见效推荐）：落地【方案 A（极简沉浸条 + 侧滑抽屉/模态配置）】
* **核心优势**：
  1. 当前 `web/index.html` 与 `web/app.js` 中已经具备成熟的表格生成和模态框控制逻辑（如设置弹窗、Prompt 调优弹窗）。
  2. 仅需将原有的 `rules-accordion` 替换为紧凑的控制状态条（Summary Bar），并将原本的规则配置表单移入标准的 Drawer/Modal 组件中。
  3. 彻底解决用户最在意的“垂直高度压抑”、“操作繁琐”、“动线混乱”问题，工期短、见效快、无兼容破坏风险。

### 第二阶段（高阶体验打磨）：
1. 在常用标签库引入**分类标签池**（如：【机构类】甲方/乙方/组织代码；【人员类】法人/姓名/身份证；【财务类】账号/金额）。
