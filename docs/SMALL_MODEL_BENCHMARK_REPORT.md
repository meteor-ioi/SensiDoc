# 针对超轻量端侧小模型（450M~1.5B）敏感信息抽取的输出格式与遵循度评估报告

> 本报告基于对本地测试集（`/Users/icychick/Desktop/测试提取/`）、8 组真实工业品盲测集（demo3 ~ demo10）、10 轮系统提示词演进（v01 ~ v10）以及《小模型训练策略建议.md》的深入分析，专门针对 SensiDoc 系统在超轻量端侧模型（如 Qwen2.5-Coder-1.5B 与 LFM2.5-VL-450M）环境下的提取格式与遵循度提出工程建议。

---

## 一、 当前三元组格式（方案 A）的瓶颈分析

在当前的系统提示词与接口定义中，默认引导模型输出完整的敏感信息三元组：
```json
[
  {
    "text": "从原文提取到的敏感原词",
    "category": "所属敏感字段名称",
    "risk_level": "风险等级（高危/中危/低危）"
  }
]
```

经大量真实用例盲测，该格式在 450M~1.5B 端侧小模型上存在以下物理瓶颈：

1. **认知过载与注意力分散（Attention Dilution）**：
   - 450M~1.5B 模型的参数容量仅为 70B 大模型的 1/50 ~ 1/150，工作记忆（Working Memory）空间狭窄；
   - 要求模型同时完成 **“实体识别 (text) + 实体归纳分类 (category) + 风险定级 (risk_level)”** 三重复合任务，超出了小模型零样本领悟的物理上限；
   - 模型被迫将计算量分配到判定“什么是高危/低危”以及组织复杂的 JSON Key 结构上，导致对正文关键敏感实体的感知力下降，**极易诱发严重漏抽**。

2. **格式损毁与复读死循环（Repetition Trap）**：
   - 当遇到复杂文本、跨行段落或多实体密集区域时，嵌套的 Object 数组结构容易导致小模型的括号匹配失准；
   - 一旦在生成 `"risk_level"` 时产生幻觉，模型倾向于反复吐出相似模板字串，导致无法在 max_tokens 限制前优雅结束，首字时延（TTFT）大幅拉长。

---

## 二、 格式方案横向对比与稳定性规律

结合迭代测试记录与小模型行为特征，对比四种常见输出格式：

| 方案 | 格式形态 | 小模型认知负载 | 遵循度与稳定性 | 首字时延 (TTFT) | 综合评价 |
|---|---|---|---|---|---|
| **方案 A (当前三元组)** | `[{"text":"...", "category":"...", "risk_level":"..."}]` | 极高（找词+分类+定级） | **最差**。极易漏抽、幻觉，长文本格式损毁率高。 | 慢（需要长提示词预热定义分类标准） | ❌ 过于繁琐 |
| **方案 B (纯扁平字符串数组)** | `["敏感词1", "敏感词2"]` | **极低**（仅单点剥离） | **最优**。完全契合小模型天然的序列截取能力，零格式死循环。 | **极快**（毫秒级首字响应） | ⭐ **最佳推荐** |
| **方案 C (键值对紧凑)** | `[{"text":"...", "category":"..."}]` | 中等（找词+分类） | 中等。免除臆造风险等级，但仍存在 Object 嵌套。 | 较快 | ⚠️ 备选（需配合 API 约束） |
| **方案 D (分类字典)** | `{"身份证": ["..."], "手机号": ["..."]}` | 偏高（分类先导） | 较差。强制要求模型先输出 Key，违背文本顺序扫描直觉，易出现空数组。 | 较慢 | ❌ 不推荐 |

### 核心工程规律：
> **输出结构越扁平、嵌套层级越少、不强加分类与定级先验知识的任务，端侧小模型的遵循度越高、TTFT 越短、死循环率越趋近于 0。**

## 三、 SensiDoc 系统的最终落地与架构解耦方案

为了兼顾 **小模型极致的遵循度** 与 **SensiDoc 完整的审计功能**，推荐采用 **“端侧极简提取 + 后端规则引擎映射”** 的解耦架构：

```text
                    [ 待审计原始文档 Markdown ]
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
      【正则极速提取管道】               【本地端侧小模型 AI 提取】
      (身份证/手机号/邮箱等)              (llama-server @ 8081)
                 │                               │
                 │              提示词要求：仅输出扁平字符串数组
                 │              格式：["张三", "13800138000"]
                 │                               │
                 │                               ▼
                 │                   【后端双模弹性解析引擎】
                 │                   (支持 Objects / Strings)
                 │                               │
                 │                   【规则引擎后处理映射】
                 │                   - 正文坐标精准回填 (positions)
                 │                   - 自动根据字段特征进行 category 归类
                 │                   - 自动赋予预设的 risk_level
                 │                               │
                 └───────────────┬───────────────┘
                                 │
                                 ▼
                     【位置冲突消解与合并去重】
                                 │
                                 ▼
                    [ 完整结构化敏感词审计清单 ]
```

### 1. 模型端提示词极简化（方案 B 契约）
提示词中明确正向规则，剥离多行示例与负向约束，仅约束纯数组：
```text
【输出要求】：必须且仅能输出合法的 JSON 字符串数组，严禁任何额外解释或 Markdown 标记。格式如下：
["提取到的敏感原词1", "提取到的敏感原词2"]
如果原文没有敏感信息，直接输出空数组 []。
```

### 2. 后端双模弹性解析实现（已在 `src/extractor.rs` 落地）
利用 Rust `serde_json` 的 `#[serde(untagged)]` 特性，后端同时无缝兼容传统对象与扁平数组：
```rust
#[derive(Deserialize)]
#[serde(untagged)]
enum LlmRawOutput {
    Objects(Vec<LlmItemObject>), // 兼容三元组对象格式
    Strings(Vec<String>),         // 原生支持极简字符串数组
}
```
当小模型返回 `["张三", "13800138000"]` 时，后端会自动提取原文、计算字符偏移量 `positions`，并与配置规则中的分类和风险等级完成自动匹配与补充。

## 四、 进阶演进建议：本地专用轻量微调 (LoRA)

如需让 450M~1.5B 模型在无提示词约束下也能具备极高的实体截取与去重本能，可参考《小模型训练策略建议.md》：
1. **数据准备**：使用商用大模型（如 GPT-4o / DeepSeek-V3）对 50~100 篇脱敏文档蒸馏出标准的 `{"input": "...", "output": "[\"...\"]"}` Alpaca 格式样本；
2. **Mac 本地一键微调**：使用专为 Apple Silicon 优化的开源桌面工具 **M-Courtyard** (基于 Apple mlx-lm) 或 **LLaMA-Factory WebUI**；
3. **模型导出与替换**：微调后直接导出为 `GGUF (Q4_K_M)` 格式，放置于 SensiDoc 的 `models/` 目录即可热载入使用。
